# Product Requirements Document (PRD)

## 1. هدف سند

تعریف الزامات نسخه اول ابزار داخلی تولید مدل سه‌بعدی ساختمان‌های اطراف پروژه، به‌گونه‌ای که تیم محصول، طراحی و توسعه برداشت یکسانی از دامنه و معیار پذیرش داشته باشند.

## 2. ورودی پروژه

| فیلد | نوع | الزام | توضیح |
|---|---|---:|---|
| `name` | string | بله | نام یکتا و قابل‌خواندن پروژه |
| `latitude` | decimal | بله | WGS84، بازه `-90..90` |
| `longitude` | decimal | بله | WGS84، بازه `-180..180` |
| `radius_m` | integer | بله | معمولاً ۱۰۰ تا ۲۰۰ متر |
| `reference_pool` | folder | خیر | تصاویر مرجع که تیم برای همان پروژه دستی قرار می‌دهد |

## 3. خروجی پروژه

- تصویر هوایی اصلی محدوده
- تصویر هوایی کدگذاری‌شده با شناسه ساختمان‌ها
- فهرست ساختمان‌ها و metadata آن‌ها
- پنج تصویر مستقل `front/back/left/right/top` برای هر ساختمان تأییدشده
- یک FBX مستقل برای هر ساختمان تکمیل‌شده
- گزارش وضعیت، خطاها، منابع و تلاش‌ها

تمام مدل‌ها باید با واحد متر و ارتفاع منطبق بر تخمین تأییدشده تحویل شوند. جانمایی و rotation جهانی خارج از دامنه است.

## 4. گردش کار اصلی

### 4.1 ایجاد و آماده‌سازی

1. کاربر پروژه را ایجاد می‌کند.
2. سیستم دسترسی اینترنت، فضای دیسک، تب‌ها/نشست‌ها و Telegram را بررسی می‌کند.
3. تصویر هوایی محدوده دریافت می‌شود.

### 4.2 تشخیص ساختمان و ارتفاع

1. footprint ساختمان‌های داخل شعاع شناسایی می‌شود.
2. ساختمان‌ها با `B001...Bnnn` کدگذاری می‌شوند.
3. ارتفاع و تعداد طبقات با بهترین شواهد موجود تخمین زده می‌شود.
4. تصویر هوایی کدگذاری‌شده ساخته می‌شود.

### 4.3 تأیید اول: Map Approval

کاربر باید بتواند ساختمان را اضافه/حذف، footprint را اصلاح، و ارتفاع یا تعداد طبقات را ویرایش کند. پس از تأیید، نسخه snapshot داده‌ها ثبت می‌شود.

### 4.4 جمع‌آوری مرجع

1. سیستم تصاویر مرتبط ساختمان هدف را در Google Street View و نشان ۳۶۰ بررسی می‌کند.
2. تصویر بهتر بر مبنای وضوح، زاویه، visibility و occlusion انتخاب می‌شود.
3. اگر مرجع واقعی کافی نبود، تصاویر موجود در استخر دستی همان پروژه رتبه‌بندی می‌شوند.
4. اگر هیچ گزینه مناسبی نبود، ساختمان `MissingReference` می‌شود و تیم مطلع می‌گردد.

سیستم در MVP برای پرکردن استخر مرجع، محله یا شعاع ۵۰۰ متری را crawl نمی‌کند.

### 4.5 تأیید دوم: Reference Approval

کاربر باید بتواند تصاویر را تأیید/رد، مرجع دیگری انتخاب یا آپلود، جهت تقریبی نما و ارتفاع را اصلاح کند.

### 4.6 تولید نما

1. سیستم با کنترل وب ChatGPT یک شیت ثابت پنج‌جهتی می‌سازد.
   ساختمان باید دارای رنگ و تکسچر واقعی نما بر اساس تصاویر مرجع باشد؛ خروجی سفید، طوسی، clay، monochrome یا بدون تکسچر قابل قبول نیست. پس‌زمینه تمام نماها باید خاکستری تیره یکنواخت و دارای جدایی واضح با سیلوئت ساختمان باشد.
2. شیت با template مشخص به پنج فایل مستقل برش می‌خورد.
3. consistency پایه تصاویر به‌صورت خودکار بررسی می‌شود.

### 4.7 تأیید سوم: View Approval

کاربر می‌تواند کل مجموعه یا هر نما را رد کند، توضیح اصلاحی بدهد و تولید مجدد انجام دهد. تنها مجموعه تأییدشده به Hunyuan می‌رود.

### 4.8 تولید و اعتبارسنجی FBX

1. تصاویر مستقل در فیلدهای جهت‌دار Hunyuan بارگذاری می‌شوند.
2. مدل ساخته و دانلود می‌شود.
3. فایل بازخوانی و ابعاد آن بررسی می‌شود.
4. مدل به ارتفاع تأییدشده scale و به FBX استاندارد صادر می‌شود.
5. artifact و checksum ثبت می‌شود.

## 6. الزامات غیرعملکردی

- **Reliability:** عملیات باید idempotent یا دارای guard در برابر تکرار ناخواسته باشد.
- **Durability:** وضعیت قبل و بعد از هر عملیات خارجی persist شود.
- **Observability:** log ساختاریافته، timeline پروژه و خطای قابل‌فهم برای کاربر.
- **Security:** توکن‌ها و sessionها خارج از project artifacts و logها نگهداری شوند.
- **Maintainability:** هر provider در adapter مستقل با selectorهای versioned باشد.
- **Usability:** وضعیت همه ساختمان‌ها در یک dashboard و تأیید batch با امکان override موردی.
- **Performance:** زمان پایان محدودیت اصلی نیست؛ UI در زمان کار پس‌زمینه responsive بماند.

## 7. وضعیت‌ها

`Draft → Preflight → Detecting → AwaitingMapApproval → CollectingReferences → AwaitingReferenceApproval → GeneratingViews → AwaitingViewApproval → GeneratingModel → ValidatingModel → Completed`

هر stage می‌تواند به `NeedsReview` یا `Paused` برود. `Failed` فقط برای خطای غیرقابل‌بازیابی پروژه استفاده می‌شود.

## 8. قواعد retry

- دو تلاش خودکار برای خطاهای transient با backoff.
- کپچا، logout و نبود مرجع خطای transient نیستند و مستقیماً intervention می‌خواهند.
- retry باید attempt جدا با log و artifact جدا بسازد.
- کاربر می‌تواند شمارنده را reset و stage را دستی دوباره اجرا کند.

## 9. معیارهای پذیرش MVP

1. پروژه ۱۰ تا ۲۰ ساختمانی بدون از‌دست‌رفتن وضعیت تا پایان اجرا شود.
2. سه تأیید در UI قابل انجام و پس از آن resume خودکار باشد.
3. خطای یک ساختمان مانع ساختمان دیگر نشود.
4. restart برنامه پردازش تکمیل‌شده را تکرار نکند.
5. FBX خروجی در Blender باز شود و ارتفاع آن در tolerance پنج درصد یا ۰٫۵ متر از مقدار هدف باشد؛ هرکدام بزرگ‌تر است.
6. اعلان‌های تعریف‌شده به Telegram برسند و failure ارسال اعلان، pipeline را متوقف نکند.
7. secrets در log، report و پوشه پروژه ظاهر نشوند.

## 10. عدم قطعیت‌های فنی برای Spike اولیه

- پایداری دسترسی برنامه‌پذیر به Google/نشان و metadata زاویه دوربین
- کیفیت footprint detection برای نمونه‌های واقعی تهران
- امکان کنترل پایدار وب ChatGPT و Hunyuan با profile اختصاصی
- قابلیت import/export مطمئن FBX توسط Blender در حالت headless
